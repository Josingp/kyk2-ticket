# 신인감독 김연경2 · 모바일 초대 티켓

이름 + 연락처 뒤 4자리를 입력하면 본인 초대 티켓이 화면에 표시되는 정적 웹앱입니다.
서버가 필요 없어 **GitHub Pages / Vercel에 그대로 배포**할 수 있습니다.

## 파일 구성

| 파일 | 용도 |
|---|---|
| `index.html` | 관람객용 티켓 조회 화면 |
| `verify.html` | 스태프용 검증 화면 (QR 스캔 시 자동 열림) |
| `admin.html` | (구 주소) 접속 시 메인 페이지 **관리자 탭**으로 자동 이동 |
| `api/` | Vercel 서버 함수 — DB 조회(`/api/db`) · 관리자 발행/명단(`/api/admin`) · 좌석 체크인(`/api/checkin`) · 좌석 공유(`/api/share`) |
| `data/db.json` | 백업용 정적 DB (서버 저장소가 없거나 접속 불가할 때만 사용) |
| `assets/config.js` | 행사명 · 날짜 · 고지 문구 · 회차 솔트 설정 |
| `tools/명단_양식.xlsx` | 명단 입력 양식 |

## 운영 흐름

1. `tools/명단_양식.xlsx` 형식으로 명단 작성 — 열: `이름 / 연락처 / 구역 / 좌석 / (등급)`
   같은 사람의 좌석이 여러 개면 행을 여러 줄로 입력합니다.
2. 배포 주소 상단의 **관리자 탭**에서 비밀번호로 로그인한 뒤 엑셀을 올리면
   브라우저에서 암호화된 뒤 **서버(Upstash Redis)에 바로 적용**됩니다. 재배포 없이 즉시 반영됩니다.
   - 열 구성: **대분류 · 소분류(동반인, 선택) · 연락처 · 구역 · 좌석 · 등급(선택)**. 조회는
     대분류+연락처 뒤 4자리로 하며, 소분류가 있는 좌석은 티켓에 `대분류 (소분류)`로 표기됩니다.
   - **증분 적용**: 서버 명단과 비교해 **바뀐 사람만 재암호화**합니다. 안 바뀐 사람은 확인코드·
     암호문·공유 링크가 그대로 유지되므로, 수정된 엑셀을 몇 번을 다시 올려도 안전합니다.
3. 같은 탭의 **서버 명단 조회 · 수정**에서 현재 명단을 표로 불러와 고치거나 행을 추가·삭제하고
   다시 적용할 수 있습니다. 여기도 증분 적용이라 바뀐 행의 인원만 갱신됩니다.
4. `스태프_확인용_명단.xlsx`는 관리자 탭에서 언제든 다시 내려받아 입장 스태프에게만 전달합니다. (확인코드 포함)
5. 서버 적용이 실패하는 환경(GitHub Pages, Upstash 미설정)에서는 예전처럼 `db.json`을 내려받아
   저장소의 `data/db.json`을 교체하는 백업 경로가 그대로 동작합니다.

## 서버 저장소(Upstash) 설정 — 최초 1회

즉시 반영 기능은 Vercel 서버 함수 + Upstash Redis를 사용합니다. (봉고조아/배구 좌석툴과 같은 조합)

1. Vercel 프로젝트 → **Storage** → **Upstash Redis** 생성·연결 (Marketplace 연동 시
   `KV_REST_API_URL` / `KV_REST_API_TOKEN` 환경변수가 자동 주입됩니다)
   또는 Upstash 콘솔에서 REST URL/TOKEN을 복사해 환경변수
   `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` 으로 직접 등록해도 됩니다.
2. 등록 후 **Redeploy** 한 번.
3. 관리자 비밀번호를 바꾸려면: 환경변수 `ADMIN_PASSWORD_SHA256`(새 비밀번호의 SHA-256 hex)을
   등록하고, `index.html`의 `ADMIN_HASH` 상수도 같은 값으로 교체하세요.
4. 관리자 API는 IP당 10분에 30회로 제한되어 무차별 대입을 막습니다.

명단 원본(이름·연락처·좌석·확인코드)은 **Upstash 안에만** 저장되고, 공개적으로 내려받을 수 있는
`/api/db` 응답과 `data/db.json`에는 지금처럼 **암호문만** 들어갑니다.

## 배포

**Vercel (권장):** vercel.com → Add New Project → 이 저장소 import → Framework: Other → Deploy
**GitHub Pages:** 저장소 Settings → Pages → Deploy from a branch → `main` / root

## 좌석 단위 입장 체크인 (한 명이 여러 매를 나눠 입장하는 경우)

한 사람 명의로 20매를 받아 일행이 **각자 따로 도착해도** 좌석 하나씩 입장 처리할 수 있습니다.

- **입구 처리 방법 ① — 관람객 화면에서:** 관람객 티켓 하단의 **[입장 확인 (스태프)]** 버튼을
  스태프가 누르고 확인만 하면(비밀번호 불필요) 그 좌석이 즉시 입장 처리됩니다. 처리된 티켓은
  관람객 화면에서 **회색 + "입장 완료" 도장**으로 바뀌어 재사용이 불가능해 보입니다. (10초 주기 자동 갱신)
  입장 처리는 티켓 소지자에게 불리한 방향이라 비밀번호가 없어도 악용 여지가 없고,
  **취소(되돌리기)만 스태프 비밀번호가 필요**해 회색 해제 후 재사용하는 수법이 차단됩니다.
- **입구 처리 방법 ② — QR 스캔(verify.html)에서:** QR을 찍으면 그 코드의 전 좌석과 입장 여부가
  나오고, 스태프 모드(비밀번호 1회 입력, 기기별 세션 유지)에서 좌석별 [입장]/[취소] 또는
  [전체 입장 처리]를 누르면 됩니다. 여러 게이트에서 동시에 처리해도 안전합니다(좌석 단위 저장).
- **현장 위치 배지:** 관람객 화면 상단에 GPS 기준 "📍 현장 인증(행사장 반경)" 배지가
  표시됩니다. 실내에서는 GPS가 부정확할 수 있어 **참고용**이며, 입장 판정은 스태프 확인이 기준입니다.
  좌표·반경은 `assets/config.js`의 `venue`에서 회차별로 수정합니다.
- **위치 기반 자동 입장(미검표 대비):** 티켓 화면이 열려 있는 동안 기기가 행사장까지의 거리만 계산해
  반경 안일 때 상태 조회에 거리·정확도를 실어 보냅니다(좌표는 전송·저장하지 않음). 서버는 좌석별 체류를
  `tickets:<salt>:presence`에 집계하고, `config.js`의 `autoCheckin` 규칙(기본: 입장 시작 이후 보고 3회·1분 체류)을
  만족하면 그 기기에 표시 중인 미입장 좌석을 **자동 입장**으로 기록합니다(`tickets:<salt>:auto` 표식).
  자동 입장은 티켓에 "현장 위치로 자동 확인됨"으로, 현황판에는 파란 `✓자동` 칩으로 구분되며, 게이트에서 스태프가
  [입장 확인]을 누르면 정식 입장으로 승격됩니다. 선물 링크로 넘긴 좌석은 소유자 기기의 체류로는 처리되지 않고
  수신자 화면의 체류로만 처리됩니다.
- **위치 기반 미검표 보정(관리자 탭):** 행사 중·후에 아직 미입장인데 현장 체류 기록이 있는 좌석을
  체류 시간·보고 횟수와 함께 나열하고, 선택한 좌석을 일괄 자동 입장으로 처리합니다.
- **실시간 입장 현황(관리자 탭):** 누가 왔고 안 왔는지 사람·좌석 단위로 집계됩니다.
  진행률, 전원/일부/미입장 필터, 이름·연락처 검색, 8초 자동 새로고침을 지원하고,
  좌석 칩을 눌러 수동 입장 처리/취소(정정)도 가능합니다.
- 체크인 기록은 Upstash의 별도 해시 키(`tickets:<salt>:checkin`)에 저장되며 티켓 DB와 분리되어
  있어, 명단을 수정·재발행해도 좌석이 그대로면 입장 기록이 유지됩니다.
- **동시 처리 안전(선착순)**: 같은 이름으로 여러 명이 조회해 들고 있거나 선물 링크가 여러 기기에
  열려 있어도, 한 좌석의 입장 처리는 **가장 먼저 누른 한 번만** 기록됩니다. 폴링 지연 사이에
  다른 게이트가 같은 좌석을 다시 누르면 "⚠ 이미 HH:MM에 입장 처리된 좌석" 경고가 떠서
  중복 입장 시도를 현장에서 바로 잡을 수 있습니다. (최초 입장 시각은 절대 덮어써지지 않음)

## 좌석 1매 선물(공유) 링크

한 명이 여러 매를 받은 뒤 일행에게 좌석을 나눠줄 때 씁니다.

- **1매만 받은 사람은 양도 불가**: 명단 기준 좌석이 1매인 사람의 티켓에는 선물 버튼 대신
  **"🔒 본인 외 사용 불가"** 안내가 표시됩니다. 서버(`/api/share`)도 링크 생성을 거부하고, 이전에 만들어진
  링크가 있어도 열리지 않습니다(`not_transferable`). 명단에서 2매 이상으로 바꾸면 즉시 다시 허용됩니다.
- 본인 티켓 화면에서 좌석 카드마다 **[🎁 이 좌석만 일행에게 보내기]** 를 누르면 그 좌석 전용
  링크(`?g=토큰`)가 만들어집니다. 카카오톡 등으로 링크만 보내면 됩니다.
- 받은 사람은 이름·연락처 입력 없이 링크만으로 **그 좌석 1매짜리 티켓 화면**을 봅니다.
  실시간 시계·QR·입장확인 버튼·좌석 위치 안내가 모두 동일하게 작동합니다.
- **여러 매 묶음 링크**: 티켓 목록 아래 "여러 좌석 한 번에 보내기"에서 좌석을 골라
  링크 하나로 묶어 보낼 수 있습니다. 같은 조합이면 항상 같은 링크가 나옵니다.
- **링크는 행사 종료 시각(`config.js`의 `schedule.end`)까지 유효**하며, 종료 후에 만든 링크만 생성 후
  6시간 뒤 만료됩니다. 만료된 링크를 열면 "만료된 티켓입니다 — 초대자에게 새 링크를 다시 요청하세요"가
  표시되고, 같은 좌석 조합으로 다시 만들면 새 링크가 발급됩니다. 생성 시 만료 시각이 함께 안내됩니다.
- 유효 기간 안에서는 좌석·이름이 그대로면 명단을 수정해도 링크가 유지되고, 묶음 중 일부 좌석이
  변경되면 **남은 좌석만으로 계속 열리며** "N매 제외" 안내가 표시됩니다. **[삭제]** 는 즉시 회수.
- 링크 생성·삭제는 티켓 소유자만(확인코드 소지 = 본인 증명), 수신자는 무작위 12자리 토큰으로만
  접근합니다. 토큰과 좌석 매핑은 Upstash(`tickets:<salt>:share`)에 저장됩니다.

## 캡처(스크린샷) 대응

웹 기술로는 OS 차원의 스크린샷 자체를 막을 수 없습니다(네이티브 앱 전용 권한).
대신 **캡처가 찍혀도 쓸모없게** 만드는 3중 장치를 적용했습니다.

1. **확인코드 회전 마스킹** — 코드의 한 글자가 0.65초마다 돌아가며 가려져,
   어느 순간의 스크린샷에도 전체 코드가 담기지 않습니다. (길게 누르면 잠시 전체 표시)
2. **30초 주기 보안 패턴** — 티켓과 스태프 검증 화면에 같은 색·단어 패턴이 표시됩니다.
   30초가 지난 캡처는 패턴이 달라 입구에서 즉시 판별됩니다. (실시간 시계와 이중 확인)
3. **선택·복사·우클릭 차단** + 입장 처리 시 티켓 회색 전환(재사용 무력화).

## 위조방지 구조

- **실시간 요소** — 초 단위 KST 시계, LIVE 펄스, 화면을 훑는 광택 애니메이션, 이름+현재시각 워터마크.
  캡처 이미지는 시계가 멈춰 있으므로 입장 시 실시간 화면만 인정하면 됩니다.
- **확인코드** — 발급 시 무작위 생성되어 암호문 안에만 존재합니다. 명단에 없는 사람은 유효한 코드를
  만들 수 없고, 스태프는 `verify.html`(티켓 QR)이나 스태프 명단으로 즉시 대조할 수 있습니다.
- **암호화 DB** — `db.json`에는 이름·연락처·좌석이 평문으로 들어 있지 않습니다.
  올바른 이름+뒤 4자리를 아는 본인만 자기 티켓을 복호화할 수 있습니다. (PBKDF2 10만 회 + AES-GCM)
- 검증은 반드시 **공식 배포 주소의 verify.html**에서 하세요. 확실히 하려면 종이 명단(스태프 확인용)과
  코드 대조가 최종 기준입니다.

## 개인정보 보호 (안전성 확보조치)

개인정보 보호법상 안전조치 의무에 대응하도록 다음을 구현했습니다. (최종 법적 판단은 사내 담당 검토 권장)

- **수집·보관 최소화** — 관람객 조회 입력값(이름·뒤 4자리)은 서버로 전송되지 않고 기기 안에서만
  사용됩니다. 서버 명단의 연락처는 가운데 자리를 버리고 `010****1234` 형태로만 보관합니다.
  (연락이 필요하면 원본 엑셀 파일을 기준으로 하세요 — 원본은 회사 내부에서만 관리)
- **저장 암호화** — 환경변수 `DATA_KEY` 설정 시 서버 명단을 AES-256-GCM으로 암호화해 저장합니다.
  Upstash에는 암호문만 남아 저장소 유출 시에도 명단이 노출되지 않습니다.
  설정: `openssl rand -hex 32` 등으로 만든 무작위 문자열을 Vercel → 프로젝트 → Settings →
  Environment Variables 에 `DATA_KEY` 로 등록 → Redeploy → 관리자 탭에서
  **명단 불러오기 → 변경사항 서버에 적용**을 한 번 실행하면 기존 평문 명단이 암호문으로 전환됩니다.
  미설정 상태면 관리자 탭 상단에 경고가 표시됩니다.
- **접근 통제 (2단계 인증)** — 환경변수 `TOTP_SECRET` 설정 시 관리자 로그인은
  **비밀번호 + Microsoft Authenticator 등 표준 인증앱의 6자리 OTP**(RFC 6238)가 필요합니다.
  소스에서 비밀번호가 복원되더라도 인증앱 없이는 명단에 접근할 수 없습니다.
  설정: ① 인증앱에 OTP 등록 QR을 스캔(또는 비밀키 수동 입력) ② Vercel 환경변수에
  같은 비밀키를 `TOTP_SECRET`으로 등록 → Redeploy. (`DATA_KEY`가 함께 있어야 활성화)
  - **역할 분리**: 게이트 스태프(verify.html 스태프 모드)는 비밀번호만으로 12시간 세션을 받되
    입장 처리/취소만 가능하고, 명단 열람·발행·파기는 관리자(OTP) 전용입니다.
  - IP당 실패 20회 잠금은 비밀번호·OTP 모두에 적용됩니다. 브라우저에는 비밀번호 대신
    만료형 세션 토큰만 저장됩니다.
- **전송 보호·보안 헤더** — 전 구간 HTTPS, `vercel.json`으로 CSP · X-Frame-Options(DENY) ·
  nosniff · Referrer-Policy(no-referrer) · Permissions-Policy 적용.
- **파기** — 관리자 탭 하단 **[행사 데이터 전체 파기]** 버튼으로 서버의 명단·DB·입장 기록·공유 링크를
  일괄 삭제합니다("파기" 입력 확인 필요). 저장소의 `data/db.json` 백업, 출력한 스태프 명단,
  원본 엑셀은 별도로 삭제해야 합니다.
- **고지** — 관람객 화면 하단 "개인정보 처리 안내"에서 수집·이용·파기 내용을 안내합니다.
- **위치 정보** — 현장 배지용 위치는 기기에서만 확인하며 서버 전송·저장이 없습니다.

## 외부 CDN 의존 제거 (국내망 차단 대응)

QR 라이브러리와 엑셀 라이브러리는 저장소에 직접 포함되어(`assets/qrcode.min.js`,
`assets/xlsx.full.min.js`) 외부 CDN(jsdelivr 등)이 통신사·보안망에서 차단되어도
티켓·관리자 기능이 정상 동작합니다. 만에 하나 QR 생성이 실패해도 티켓은 그대로 표시되고
QR 자리에만 "확인코드로 검증 가능" 폴백이 뜹니다. 글꼴만 CDN을 쓰므로 차단망에서는
기본 글꼴로 표시됩니다(기능 무관).

## 오프라인 · 저속망 대응 (현장 통신 장애)

체육관 실내에서 LTE가 끊기거나 느려도 운영이 계속되도록 3중으로 대비했습니다.

- **티켓은 오프라인에서도 유효** — 시계·보안 패턴·QR·워터마크가 전부 기기에서 동작하므로,
  이미 열어둔 티켓은 통신이 끊겨도 게이트 육안 검증이 그대로 가능합니다.
- **서비스 워커 캐시(sw.js)** — 한 번이라도 접속한 기기는 페이지·폰트·티켓 DB가 기기에
  저장되어, 완전 오프라인에서도 티켓 조회 화면이 열립니다. DB는 네트워크 우선(4초) →
  실패 시 마지막 캐시본을 쓰므로 느린 망에서도 빠르게 뜹니다.
- **입장 처리 오프라인 큐** — 관람객 화면·QR 검증 화면에서 입장 처리가 통신 실패하면
  기기에 저장하고 "동기화 대기"로 표시한 뒤, 연결이 복구되는 즉시 자동으로 서버에 반영합니다.
  (입장 취소는 정합성을 위해 온라인에서만 가능) 화면 상단에 오프라인 배너가 표시됩니다.
- **운영 팁**: 초대 안내 문자에 "행사장 도착 전 티켓을 한 번 열어봐 주세요"를 넣고,
  스태프는 입장 시작 전 verify 화면을 미리 한 번 열어두면(캐시 적재) 통신 장애에도 안전합니다.

## 동시 접속 대비 (부하 설계)

행사 당일 수백 명이 동시에 티켓을 열어도 무료 플랜 한도 안에서 동작하도록 3중으로 줄였습니다.

1. **서버 함수 메모리 캐시** — 명단·체크인 현황·DB를 함수 인스턴스 메모리에 3~10초 캐시.
   좌석 체크인 등 쓰기가 일어나면 즉시 무효화되어 실시간성은 유지됩니다.
   (측정: 10초 창에서 상태 폴링 300회 + DB 조회 60회 → Redis 명령 3건, 이전 대비 99.8% 절감)
2. **엣지 CDN 캐시** — `/api/db` 응답에 `s-maxage=15`를 적용해 접속이 몰려도
   오리진(함수+Redis)에는 15초에 1번만 도달합니다.
3. **클라이언트 폴링 절제** — 상태 갱신 주기를 12~16초 무작위로 분산하고,
   화면이 꺼지거나 백그라운드로 가면 폴링을 멈췄다가 다시 볼 때 즉시 갱신합니다.

무차별 대입 방지용 실패 카운터(비밀번호)만 Redis에 남기고, 폴링·공유 조회 등
인증 없는 요청의 사용량 제한은 인메모리로 처리해 Redis를 소모하지 않습니다.

## 안정성 점검 (행사 전 감사 반영)

- 현장 네트워크가 불안정해도 입장확인 버튼이 사라지지 않고 "연결 대기 중"으로 자동 재시도합니다.
- 보안 패턴·세션은 **서버 시간 기준**으로 동기화되어 기기 시계가 틀려도 오판하지 않습니다.
- 관리자 여러 명이 동시에 명단을 수정하면 서버가 충돌(409)을 감지하고 최신본 기준으로 자동 재적용합니다.
- 엑셀 연락처가 숫자 서식이라 앞자리 0이 사라진 경우 자동 복구합니다.
- 명단 발행 직후 접속한 관람객은 캐시를 우회한 최신 DB로 1회 자동 재조회합니다.
- 같은 OTP 코드는 한 번만 사용됩니다(재사용 차단). 관리자 행위(로그인·발행·입장취소·파기)는
  감사 로그로 최근 1,000건 보관되며 관리자 탭에서 열람할 수 있습니다.

## 주의사항

- 원본 명단 엑셀과 스태프 확인용 명단은 **절대 저장소에 올리지 마세요.** (`.gitignore`로 기본 차단)
- `assets/config.js`의 `salt`는 회차마다 다르게 설정하는 것을 권장하며, 바꾸면 `db.json`을 다시 생성해야 합니다.
- 회차 전환 순서: `config.js`(행사 정보·일정·salt·venue·autoCheckin) 수정 → `assets/venue-*.js` 도면 교체(`index.html`·`sw.js` 참조 경로, `sw.js`의 `VER` 증가) → 배포 → 관리자 탭에서 명단 새로 업로드. salt가 다르면 Upstash 안에서도 회차별로 완전히 분리 저장됩니다.
  (8/20 잠실학생체육관 `KYK2-JAMSIL-0820` → 8/27 장충체육관 `KYK2-JANGCHUNG-0827`, 도면 `venue-sk.js` → `venue-jc.js`)
- 지난 회차 데이터는 관리자 탭 **데이터 파기**에서 [보관 중인 회차 보기]로 확인하고, 회차 키를 직접 입력·재확인해야 파기됩니다. 파기 범위는 명단·티켓 DB·입장 기록·자동 입장 표식·위치 체류 기록·공유 링크이며, 감사 로그는 남습니다.
- 관람객 화면은 조회할 때마다 서버 DB를 먼저 받고, 서버가 비어 있으면 `data/db.json`을 사용합니다. 반영이 안 보이면 새로고침하세요.
